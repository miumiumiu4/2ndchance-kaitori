# 店ごとの置き場所の比較メモ（量産の型）

結論（◎）：**1店1リポジトリ（この型から写す）＋ 公開先は Cloudflare Pages**。最初のモニター3店はこれで始め、店が10を超えたら見直す。
料金・解約条件・ドメインの名義は作戦メモで仮置きのまま（ここでは決めない）。

例え話：A は「店ごとに別の家（家の鍵も郵便受けも別）」、B は「1棟のアパートに全店（管理人室は1つ）」。A は1軒の雨漏りがほかに移らない。B は修理が1回で済むが、1つの合鍵が全部屋に効く。

## 先に分かっていること
- GitHub Pages の利用制限（docs.github.com「GitHub Pages limits」の Usage limits）に「online business・e-commerce site・商取引を主な目的とするサイトの無料ホスティングとして使ってはいけない」旨が書かれている。**他店の商売用サイトを、こちらが月額で預かる置き場には向かない**。見本の店（今の 2ndchance-kaitori）も将来は自社ドメインへ移す予定（既定どおり）。
- Cloudflare Pages の無料枠：1アカウント100プロジェクト、1プロジェクトに独自ドメイン100（developers.cloudflare.com「Pages limits」）。商用利用の可否は規約本文で要確認（上の制限ページには記載なし）。
- 管理画面は GitHub の **1つのリポジトリの `data/*.json`** に保存する作り（`gas/Admin.gs`。`ADMIN_REPO`）。トークンもリポジトリ単位で絞っている。

## 比べた案
| 案 | 中身 | よい点 | 困る点 |
|---|---|---|---|
| **A ◎ 1店1リポジトリ** | `tools/new-store.mjs` で型を写し、店ごとのリポジトリ・受け口・トークン | 管理画面・受け口・テストが**今のまま**動く。トークンは店のリポジトリだけに効く（1店の漏れがほかに広がらない）。解約時はリポジトリごと店に渡せる | 型を直したとき、店のリポジトリへ配る手間（`git remote add template` → `git pull template main` で取り込む。data/ と content/ は店のものなので衝突しにくい） |
| B 1リポジトリ多店舗 | `stores/<id>/data/` を並べ、build を店ごとに回して別々に公開 | 型の直しが1回で全店に効く | 管理画面の保存先・トークン・テスト・Actions を全部「店ごと」に作り直す大工事。1つのトークンが全店のデータに効く。1店の data の誤りで全店の公開が止まりうる |
| C 1リポジトリ＋実行時に店を切替 | 1つのサイトが URL で店を見分ける | 置き場所は1つ | 静的サイトの作りから外れる。検索・AI 向けの店ごとのページが作りにくい。今の型と別物 |

## 公開先
| 公開先 | 向き | メモ |
|---|---|---|
| GitHub Pages | 見本・試し焼き | 上の利用制限。他店の商用サイトの本番には使わない |
| **Cloudflare Pages ◎** | 店の本番 | すでに別の試作で Cloudflare（Workers）を使っている。GitHub のリポジトリをつなぐと push で公開。店名義のドメインをつなげる（名義は仮置きの論点） |
| 店のレンタルサーバー | 店がすでに持っている場合 | Actions で `_site` を送る形にすれば型はそのまま使える |

## A を選んだときの決まり（案）
- 店の id ＝リポジトリ名＝`data/store.json` の `id`（英小文字）。
- `stores/<id>/answers.json`（聞き取りの答え）は型のリポジトリに残す（作り直しの元）。秘密は入れない。
- 型の直しは型のリポジトリで PR → マージ → 各店へ取り込み（店ごとに `npm test` が緑なら公開）。
- 受付データ（スプレッドシート）と Apps Script は店の Google アカウント（仮置き）。こちらは作る手伝いだけ。
